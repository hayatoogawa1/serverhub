## 1. グラフライブラリの確定

### 1.1 決定（D-UI-01）

**Recharts** を採用する（`FR-COM-05`、ダッシュボードの環境別/ステータス別/タグ別件数の棒グラフ）。

- React エコシステムで実績が長く、単純な棒グラフ・円グラフはコンポジションで簡潔に書ける。
- MUI とは別系統のライブラリだが、色は `theme.palette` の値を渡すだけで統一できる
  （データポイントごとの `fill` に `theme.palette.primary.main` 等を指定）。
- 代替案 **MUI X Charts**（`@mui/x-charts`）: 既存の MUI 9 とテーマが自動連動する利点はあるが、
  MUI 本体とのバージョン制約・API の変更頻度がやや高く、MVP で必要なのは単純な棒グラフのみ
  （requirements §13 は複雑な可視化を求めていない）のため、実績の長い Recharts を優先する。
  必要になれば dataviz 要件の拡大時に再検討する。

## 2. ルーティング（React Router 7）

### 2.1 ルート構成

`createBrowserRouter` + `RouterProvider`（ADR 0002）。SC-01〜08 / SC-404 のうち、**モーダル画面
（SC-05/06/08）は独立ルートを持たない**（§4）。

```
/login                          … SC-01 ログイン（未認証専用。認証済みでアクセスしたら "/" へ）
/ (AuthGuard 配下、共通レイアウト)
  ├─ /                          … SC-02 ダッシュボード
  ├─ /servers                   … SC-03 サーバー一覧
  ├─ /servers/:id               … SC-04 サーバー詳細（SC-05/06/08 はここからモーダルで起動）
  ├─ /maintenance-histories     … SC-07 メンテナンス履歴一覧
  └─ *                          … SC-404 Not Found
```

- `AuthGuard` でラップした親ルート配下に共通ヘッダー/ナビ（`AppLayout`）を置く
  （requirements §13.3、SC 一覧の「共通: ヘッダー / サイドナビ」）。
- パスは `CLAUDE.md` §4 の API パス命名（複数形・ケバブケース）に合わせる。

### 2.2 認証ガード（`AuthGuard`）

- `useAuthQuery`（`queryKey: ['auth', 'me']`、`GET /api/v1/auth/me`）の結果で判定する。
  Frontend のルートガードは UX 目的、実体は Backend（requirements §10.1.5）。
- **未ログイン**（`401`）→ `/login` へ `replace`。遷移先を `location.state.from` に積み、
  ログイン成功後にそこへ戻す（requirements §8.3「可能なら元の遷移先を保持」）。
- **判定中**（クエリ `isPending`）→ 共通ローディング表示（FR-COM-02）。画面のちらつきを避ける。
- `/login` に認証済みでアクセス → `/` へ `replace`（二重ログイン画面を避ける）。

### 2.3 セッション切れの横断検知（`apiClient` インターセプタ）

- `apiClient`（Axios）のレスポンスインターセプタで、**`/auth/login` 以外**の `401` を検知したら
  `queryClient` の `['auth', 'me']` を invalidate する。
- `AuthGuard` はこのクエリを見ているため、業務 API のどこで `401` が起きても自動的に再評価され
  `/login` へリダイレクトされる（個々の画面で `401` を握るコードを書かない、requirements §8.3）。
- ルーターの外（インターセプタ）から直接 `navigate()` しない。**状態（クエリ結果）をトリガーに
  `AuthGuard` が宣言的にリダイレクトする**設計とし、命令的なルーティングを分散させない。

## 4. モーダル（F6）の実装方針

### 4.1 決定（D-UI-02）

- **URL に反映しない**（`/servers/:id/edit` のような専用ルートを作らない）。一覧/詳細ページの
  ローカル状態（`useState<'create' | 'edit' | null>`）でモーダルの開閉を制御する。
- 理由：requirements F6 は「画面遷移せずに操作」が主眼で、モーダルへの直接リンク共有・ブラウザ
  戻るボタンでのモーダル制御は要件化されていない。URL 同期はモーダル用の状態管理コードを増やすだけの
  過剰設計になる（`CLAUDE.md` §4「過剰設計もしない」）。
- 保存成功時：モーダルを閉じ、該当 `queryKey` を invalidate して一覧/詳細を再取得（FR-COM-06）。
  画面全体のリロードはしない。
- 検索条件（一覧の絞り込み）は F6 と異なり **URL クエリに保持**する（requirements §13.3、既に
  02-api §2.5 で確定済み）。「一覧の検索条件」と「モーダルの開閉」は性質が違うため扱いを分ける。

## 5. データ取得・キャッシュ（TanStack Query）

### 5.1 queryKey とフック

`CLAUDE.md` §4 の階層構造を feature ごとに具体化する。

| queryKey | 対応 API | 用途 |
|---|---|---|
| `['auth', 'me']` | `GET /auth/me` | 認証状態、ヘッダーのユーザー表示 |
| `['servers', 'list', params]` | `GET /servers` | SC-03 一覧・絞り込み |
| `['servers', 'detail', id]` | `GET /servers/{id}` | SC-04 詳細（`version` を含む、編集フォーム初期値にも使う） |
| `['maintenanceHistories', 'list', params]` | `GET /maintenance-histories` | SC-07 一覧 |
| `['servers', 'detail', id, 'maintenanceHistories']` | `GET /servers/{id}/maintenance-histories` | SC-04 内の履歴セクション（FR-MNT-03） |
| `['tags', 'suggest', prefix]` | `GET /tags/suggest` | サジェスト（絞り込み・フォーム共通） |
| `['dashboard', 'summary']` | `GET /dashboard/summary` | SC-02 |

- `params` はページング・ソート・絞り込み条件のオブジェクトをそのままキーに含める
  （TanStack Query の既定シリアライズに任せる。手動で文字列化しない）。

### 5.2 Mutation 後の invalidate ルール

| 操作 | invalidate 対象 |
|---|---|
| サーバー登録・編集・削除 | `['servers', 'list']`（全 params）、`['servers', 'detail', id]`、`['dashboard', 'summary']`、`['tags', 'suggest']`（新規タグの可能性） |
| メンテナンス履歴登録 | `['maintenanceHistories', 'list']`、`['servers', 'detail', serverId, 'maintenanceHistories']`、`['dashboard', 'summary']` |
| ログイン成功 | `['auth', 'me']` を成功レスポンスの内容で更新（再フェッチ不要、`setQueryData`） |
| ログアウト | `queryClient.clear()`（全キャッシュ破棄。次ユーザーへの残留を避ける衛生対策） |

- **`refetchInterval` を持つクエリは作らない**（S8、requirements §10.1.3）。ポーリングによる
  セッション延命を避ける。

### 5.3 ローディング・エラー

- 各 hook は TanStack Query の `isPending`/`isError` をそのまま Page/Feature に渡す。
  独自のローディング状態変数を作らない。
- 一覧・詳細取得エラー（`401` 以外）は画面内にエラー表示（FR-COM-01）。`401` は §2.3 の横断処理に
  任せ、画面側で個別ハンドリングしない。
- Mutation のエラーは呼び出し元（フォーム/確認ダイアログ）でトースト表示 + フィールドエラーが
  あれば `errors[]`（02-api §2.4）をフォームにマッピング。

## 6. フォーム・入力

- **Frontend の入力チェックはセキュリティ対策ではなく UX**（requirements §10.1.6、Backend が
  最終防衛線）。必須・文字数上限などの軽いチェックのみ行い、複雑なルール（ホスト名重複・
  楽観ロック競合など）は API 応答（`400`/`409`）をそのまま表示する。
- 具体的なフォーム実装方式（react-hook-form 等のライブラリ採否を含む）は **[00-overview §3](00-overview.md)
  の Phase 2 確定事項に含まれず**、ADR 0002 にも記載がないため本書では確定しない。
  Phase 3（詳細設計）着手時、または Phase 6（Frontend 実装）のキックオフで改めて判断する
  （小規模な MVP のフォーム数（3 種）であれば MUI の制御コンポーネント + 軽量な自前バリデーション
  で足りる可能性がある一方、フィールド数の多いサーバーフォームでは react-hook-form 導入の価値も
  ある。判断材料を先送りするだけで、設計上のブロッカーにはならない）。

## 7. 共通コンポーネントの切り出し

`CLAUDE.md` §3「共通部品は 2 箇所目で必要になった時点で切り出す」。requirements 上ですでに
**2 画面以上での利用が確定している**ものは、先行共通化ではなく最初から `src/components/` に置く。
1 画面でしか使わないものは feature ローカルに留め、実際に 2 箇所目が出た時点で昇格する。

| 共通部品 | 利用箇所（確定分） | 備考 |
|---|---|---|
| `DataTable` + `Pagination` | SC-03（サーバー一覧）、SC-07（履歴一覧） | ソート・ページングの UI を共通化。データ列は Props で可変 |
| `StatusBadge` | SC-03 / SC-04（環境区分・ステータス） | enum → 表示ラベル・色のマッピングのみ持つ |
| `Tag` / `TagInput`（サジェスト付き） | SC-03（絞り込み）、SC-05/06（フォーム） | `features/tags` のサジェストフックを内部で利用 |
| `Modal`（Dialog ラッパー） | SC-05 / SC-06 / SC-08 | ヘッダー・フッター（保存/キャンセル）の型を統一 |
| `ConfirmDialog` | サーバー削除（FR-COM-04）+ 今後の破壊的操作 | 汎用の確認ダイアログ（メッセージ/ボタンラベルを Props 化） |
| `Loading` | 一覧・詳細・ダッシュボードなど全画面 | TanStack Query の `isPending` に連動 |
| `ErrorMessage` | 一覧・詳細・フォーム全般 | `ApiError`（02-api）をそのまま表示できる形に |
| `Notification`（トースト） | 全 mutation の成功/失敗 | 多重表示の抑制ロジックを内包（requirements FR-COM-03） |

- 1 画面のみの部品（例: ダッシュボードのグラフラッパー）は `features/dashboard/components/` に置き、
  他画面で必要になるまで共通化しない。

## 8. アクセシビリティ・レスポンシブ

- **PC 専用**（F7 確定）。ブレークポイント対応・モバイル最適化は行わない。想定解像度 1280px 幅以上。
- 最低限のアクセシビリティ（フォームの `label` 関連付け、ボタンの `aria-label`、モーダルの
  フォーカストラップは MUI `Dialog` の既定機能を利用）は MUI コンポーネントの既定に委ね、
  追加の作り込みは MVP スコープ外（requirements §5.2 に明記はないが、過剰実装を避ける）。
